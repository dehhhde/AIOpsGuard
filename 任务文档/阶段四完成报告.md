```python
class DiagnosisDTOMapper:
    """DTO 映射器"""
    
    @staticmethod
    def to_session_response(session: DiagnosisSession) -> DiagnosisSessionResponse:
        """领域模型转响应 DTO"""
        # 处理字段映射：
        # diagnosis_id -> session_id
        # service -> service_name/instance/environment
        # stage -> current_stage
        # started_at/finished_at -> created_at/updated_at
    
    @staticmethod
    def to_evidence_response(evidence: Evidence) -> EvidenceResponse:
        """证据转响应 DTO"""
    
    @staticmethod
    def to_root_cause_response(root_cause: RootCause) -> RootCauseResponse:
        """根因转响应 DTO"""
    
    @staticmethod
    def to_report_response(session: DiagnosisSession) -> DiagnosisReportResponse:
        """诊断报告转响应 DTO"""
```

**字段映射处理**：
- 领域模型使用 `diagnosis_id`，DTO 使用 `session_id`
- 领域模型使用 `service: ServiceIdentifier`，DTO 拆分为 `service_name/instance/environment`
- 领域模型使用 `stage`，DTO 使用 `current_stage`
- 领域模型使用 `started_at/finished_at`，DTO 使用 `created_at/updated_at`

### 3. 用例实现

#### TriggerDiagnosisUseCase - 触发诊断

**关键特性**：
- 使用分布式锁防止重复诊断（`diagnosis:{service_name}`）
- 锁 TTL = 300 秒，非等待模式
- 异步启动诊断（`asyncio.create_task`）
- 立即返回响应，不阻塞

```python
async def execute(self, request: TriggerDiagnosisRequest) -> TriggerDiagnosisResponse:
    """执行用例"""
    service_name = request.service_name
    lock_key = f"diagnosis:{service_name}"
    
    try:
        async with self.lock.lock(resource=lock_key, ttl=300, wait=False):
            session = await self._create_session(request)
            asyncio.create_task(self._run_diagnosis_async(session))
            
            return TriggerDiagnosisResponse(
                session_id=session.diagnosis_id,
                status="triggered",
                message=f"Diagnosis for {service_name} has been triggered"
            )
    except RuntimeError:
        raise DiagnosisAlreadyInProgressError(...)
```

#### QueryDiagnosisUseCase - 查询诊断

**查询策略**：
1. 如果指定 `session_id`：先查缓存，缓存未命中查数据库
2. 如果指定 `service_name`：查询服务的诊断历史（分页）
3. 如果指定 `status`：查询指定状态的诊断（分页）
4. 否则返回空列表

#### GetDiagnosisReportUseCase - 获取报告

**职责**：
- 根据 `session_id` 查询诊断会话
- 验证报告是否已生成
- 构建完整的诊断报告（含证据、根因）

#### CancelDiagnosisUseCase - 取消诊断

**职责**：
- 验证诊断状态（只有 `PENDING` 和 `ANALYZING` 可取消）
- 调用领域模型的 `fail()` 方法
- 清除缓存

#### RetryDiagnosisUseCase - 重新诊断

**职责**：
- 验证诊断状态（只有 `FAILED` 可重试）
- 使用原参数构建新的触发请求
- 委托给 `TriggerDiagnosisUseCase`

## 🔧 技术决策

### 1. 字段名映射

**问题**：领域模型与 DTO 字段名不一致

**解决方案**：在 `DiagnosisDTOMapper` 中处理映射：
- `diagnosis_id` → `session_id`
- `service` → `service_name/instance/environment`
- `stage` → `current_stage`
- `started_at/finished_at` → `created_at/updated_at`

**理由**：
- 领域模型保持内聚（`ServiceIdentifier` 值对象）
- DTO 平铺字段，方便前端使用
- 映射器作为翻译层

### 2. 缓存策略

**查询诊断用例采用"缓存优先"策略**：
1. 先查 Redis 缓存
2. 缓存未命中查 PostgreSQL
3. 缓存命中直接返回（未来需从缓存重建领域模型）

**触发诊断不立即缓存**：
- 诊断过程中状态频繁变化
- 缓存在诊断完成后写入（TTL = 24 小时）

### 3. 异步诊断执行

**设计**：
- 触发诊断后立即返回响应（不阻塞）
- 使用 `asyncio.create_task()` 启动后台任务
- 前端通过轮询或 WebSocket 获取进度

**优点**：
- API 响应快速（< 100ms）
- 诊断可长时间运行（数分钟）
- 防止请求超时

### 4. 分布式锁粒度

**锁 key**：`diagnosis:{service_name}`

**粒度选择**：按服务锁定，不是全局锁

**理由**：
- 不同服务可以并发诊断
- 同一服务防止重复诊断
- 粒度适中，既保证安全又提高并发

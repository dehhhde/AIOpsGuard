### 5. LangGraph 编排

#### 状态定义

```python
class DiagnosisState(TypedDict, total=False):
    """诊断状态"""
    
    # 输入
    service_name: str
    start_time: str
    end_time: str
    
    # 中间状态
    metric_evidences: List[Evidence]
    log_evidences: List[Evidence]
    trace_evidences: List[Evidence]
    
    # 输出
    root_causes: List[RootCause]
    summary: str
    
    # 错误
    error: Optional[str]
```

#### Graph 构建

```python
def build_diagnosis_graph(
    metric_agent: MetricAgent,
    log_agent: LogAgent,
    trace_agent: TraceAgent,
    rca_agent: RCAAgent,
) -> StateGraph:
    """构建诊断 Graph
    
    工作流程：
    1. Metric Agent 收集指标证据
    2. Log Agent 收集日志证据
    3. Trace Agent 收集链路证据
    4. RCA Agent 综合分析推理根因
    """
    
    # 定义节点
    async def metric_node(state: DiagnosisState) -> DiagnosisState:
        """Metric Agent 节点"""
        evidences = await metric_agent.analyze(...)
        state["metric_evidences"] = evidences
        return state
    
    # 构建 Graph
    workflow = StateGraph(DiagnosisState)
    workflow.add_node("metric_agent", metric_node)
    workflow.add_node("log_agent", log_node)
    workflow.add_node("trace_agent", trace_node)
    workflow.add_node("rca_agent", rca_node)
    
    # 定义边（顺序执行）
    workflow.set_entry_point("metric_agent")
    workflow.add_edge("metric_agent", "log_agent")
    workflow.add_edge("log_agent", "trace_agent")
    workflow.add_edge("trace_agent", "rca_agent")
    workflow.add_edge("rca_agent", END)
    
    return workflow.compile()
```

**执行顺序**：
- Metric Agent → Log Agent → Trace Agent → RCA Agent
- 当前是顺序执行，未来可改为并行执行（Metric/Log/Trace 并行收集证据）

```python
        log_agent = LogAgent(llm_client, tools)
        trace_agent = TraceAgent(llm_client, tools)

        # 构建 LangGraph
        diagnosis_graph = build_diagnosis_graph(
            metric_agent, log_agent, trace_agent, rca_agent
        )
        
        # 初始化诊断引擎
        self._diagnosis_engine = DiagnosisEngineService(graph=diagnosis_graph)
```

## 🔧 技术决策

### 1. LLM Provider 选择

**支持多种 Provider**：
- OpenAI：gpt-4, gpt-3.5-turbo
- Ollama：本地模型（兼容 OpenAI API）
- 国产模型：Qwen、DeepSeek（兼容 OpenAI API）

**决策理由**：
- OpenAI API 标准已成为事实标准
- 大部分国产模型都提供 OpenAI 兼容接口
- 通过配置 `llm_base_url` 切换 Provider

### 2. Prompt 工程

**结构化输出（JSON）**：
- 要求 LLM 只输出 JSON，无其他内容
- 使用 `json.loads()` 解析响应
- 解析失败时记录警告并返回空列表

**优点**：
- 便于程序处理
- 减少解析错误

**缺点**：
- 依赖 LLM 遵守指令
- 部分模型可能输出额外文本

**改进方向**：
- 使用 OpenAI Function Calling / Structured Outputs
- 使用正则表达式提取 JSON 部分

### 3. Agent 执行顺序

**当前实现：顺序执行**
```
Metric Agent → Log Agent → Trace Agent → RCA Agent
```

**优点**：
- 逻辑清晰，易于调试
- 减少并发复杂度

**缺点**：
- 总耗时较长

**未来优化：并行执行**
```
┌─ Metric Agent ─┐
├─ Log Agent ────┤ → RCA Agent
└─ Trace Agent ──┘
```

**实现方式**：
- LangGraph 支持 `add_conditional_edges` 和并行分支
- 或使用 `asyncio.gather` 并行执行

### 4. 报告生成

**Markdown 格式**：
- 可读性好
- 易于转换为 HTML / PDF
- 前端可直接渲染（markdown-it、marked）

**报告结构**：
1. 诊断摘要（服务、时间范围、耗时）
2. 根因分析（置信度、关联证据）
3. 证据清单（类型、来源、摘要）

### 5. 降级策略

**LLM 未启用**：
- 返回占位响应（"[LLM disabled] ..."）
- 不阻塞诊断流程

**LLM 调用失败**：
- 重试 3 次，指数退避
- 最终失败返回空证据列表
- 记录错误日志

**外部数据源不可用**：
- 工具集返回 `{"error": "..."}` JSON
- Agent 解析时跳过
- 不阻塞后续 Agent
